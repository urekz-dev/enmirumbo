# Spec: data-model

## Requirements

### Requirement: The `Business` model covers the registration fields

The system MUST persist a business with the 5 required fields of PRD §6.1 — name, category (from the catalogue), 10-digit WhatsApp, zone and the consent record for the privacy notice — and MUST support the optional ones: "¿Qué ofreces?" (max. 200 characters), home delivery (yes/no), landline phone and address or references with an optional map pin (latitude/longitude), free-text opening hours, Facebook link and photo.

The photo is NOT stored as an arbitrary URL: the business persists an **internal photo reference** (`photoKey`), which is an opaque key generated by the server when it processes the image and which only serves to locate the files in photo storage (ADR-006). That reference MUST be null when the business has no photo, MUST be unique among businesses, and MUST NEVER contain an external address, a `data:`, a URL scheme or a file system path: whoever reads this field has to be able to assume the server wrote it. The image bytes do NOT live in the database or in the repository.

#### Scenario: minimal creation with required fields only

- **WHEN** a business is created with name, category, WhatsApp, zone and consent record
- **THEN** the business is saved, all optional fields are empty and its photo reference is null

#### Scenario: full creation with optional fields

- **WHEN** a business is created including the optional fields (with map pin and with photo)
- **THEN** all values are persisted and retrievable as they were saved, including the pin coordinates and the internal photo reference

#### Scenario: the photo reference is not a URL

- **WHEN** the value stored in the photo reference of a business that uploaded an image is reviewed
- **THEN** it is the opaque key the server generated, with no URL scheme, no domain and no file system path, and it matches neither the business identifier nor its name

#### Scenario: two businesses do not share the same photo

- **WHEN** an attempt is made to save the same photo reference in two businesses
- **THEN** the database rejects the operation

### Requirement: The consent record stores which notice version it was given against

The business MUST store, next to the consent date (`consentedToNoticeAt`), the identifier of the privacy notice version that was in force when that consent was given (`consentedToNoticeVersion`). This is what turns the LFPDPPP consent record (PRD §8) into complete proof: without the version, the date points to a text that may have changed.

The two MUST travel together: no write path MUST be able to save one without the other. The version MUST be null only on cards registered **before** versioning existed; those rows MUST NOT be assigned a filler version, because nobody can say today which text they were shown. The field is a string, with no default value in the database.

The business MUST also be able to store a **re-acceptance**: the date (`reconsentedToNoticeAt`) and the version (`reconsentedToNoticeVersion`) of the last time a notice version **later** than that of its original consent record was accepted. "Later" is an ordering comparison, not an inequality: a different version may be older (a rolled-back deployment) and a consent record without a version is not comparable with any, so in those two cases no re-acceptance is recorded (the write rule lives in `business-registration`, requirement "One card per WhatsApp number"). Both null while that has not happened, and both also inseparable. The re-acceptance does NOT replace the original consent record: it complements it.

#### Scenario: creation with its version

- **WHEN** a business is created with the consent record
- **THEN** the date and the version of the notice in force at that moment are persisted, and its two re-acceptance fields are null

#### Scenario: the version does not travel alone

- **WHEN** all saved businesses are reviewed
- **THEN** none has a consent date with an empty version except cards from before versioning, and none has a re-acceptance date without a re-acceptance version (or the other way around)

#### Scenario: re-acceptance of a newer version

- **WHEN** a business whose original consent record is for version `1` accepts version `2`
- **THEN** its original consent record stays the same (same date, version `1`) and its re-acceptance fields get the date of that moment and version `2`

#### Scenario: cards from before versioning

- **WHEN** there is a card saved without a consent version, because it was registered before versioning existed
- **THEN** its version stays null, nothing assigns it a filler one and no site query fails because of it

#### Scenario: the demo seed seeds the version

- **WHEN** the fictitious business seed is run
- **THEN** they are born with the notice version in force in their consent record, except two that exist to give the admin panel its other two cases: a card from before versioning (no version and no re-acceptance) and one with the consent record of a fictitious earlier version and its re-acceptance populated

#### Scenario: the accepted version is internal data

- **WHEN** a published card is queried from the public directory
- **THEN** neither the consent version nor the re-acceptance appears in the public projection, just like `consentedToNoticeAt` and `registeredAt`

### Requirement: One card per WhatsApp number

Superseded in v2 by One card per WhatsApp number within a locality (v2) — source: ADR 0006.

The database MUST prevent, through a uniqueness constraint, two businesses from having the same WhatsApp number (PRD §6.1: "una sola ficha por número").

#### Scenario: duplicate WhatsApp

- **WHEN** an attempt is made to create a second business with a WhatsApp that already has a card
- **THEN** the database rejects the operation for violating the uniqueness constraint

### Requirement: Catalogues of categories, zones and trades with stable slug

Superseded in v2 by Catalogues of categories, zones and trades with stable slug (v2) — source: ADR 0006.

The system MUST have three persisted catalogues: the 8 categories of PRD §6.1, the zones of Appendix A and the trades of Appendix B. Each entry MUST have a unique name and slug; the slug MUST be suitable for SEO URLs: lowercase, no accents, with hyphens (e.g. `plomeria`, `haciendas-de-tizayuca`, to compose `/plomeria-haciendas-de-tizayuca`).

#### Scenario: catalogues populated by the seed

- **WHEN** the seed is run on a freshly migrated database
- **THEN** there are 8 categories, 21 zones and 49 trades, each with its slug

#### Scenario: URL-suitable slug

- **WHEN** the slug of "Plomería" and that of "Haciendas de Tizayuca" are queried
- **THEN** they are `plomeria` and `haciendas-de-tizayuca` (no capitals, accents or spaces)

#### Scenario: stable slugs across runs

- **WHEN** the seed is run again on an already populated database
- **THEN** the existing slugs do not change and no duplicate entries are generated

### Requirement: The slugs of the three catalogues do not produce ambiguous URLs at the root

Superseded in v2 by The slugs of the catalogues do not produce ambiguous URLs at the root of a locality (v2) — source: ADR 0006, ADR 0007.

The public pages for category (`/servicios-del-hogar`), trade (`/plomeria`) and trade+zone (`/plomeria-haciendas-de-tizayuca`) share the site root, so the slugs of the three catalogues MUST guarantee that **every root URL reads in only one way**. The project MUST have an automatic check on the seeded catalogues that fails —before anything is published— if any of these conditions is broken:

- no trade slug or zone slug matches a category slug;
- no slug of any of the three catalogues matches a reserved segment of the site (its own routes, PRD §6.3 and §6.4);
- no composed slug `«trade»-«zone»` matches a category slug or a trade slug;
- no composed slug `«trade»-«zone»` admits two different readings, that is, there are no two trade and zone pairs in the catalogue that produce the same URL.

It is an invariant of the seeded catalogues (8 categories, 21 zones and 49 trades with stable slug), not a model field. Reserving a name is free; migrating an already published URL is not.

#### Scenario: today's catalogues are unambiguous

- **WHEN** the check is run on the database with the three catalogues seeded
- **THEN** it passes: no root URL can be read in two ways

#### Scenario: a trade named like a category

- **WHEN** a trade whose slug matches that of a category is added to the catalogue
- **THEN** the check fails and points to the conflicting slug

#### Scenario: a trade that would shadow an own route

- **WHEN** a trade or a zone with a slug that is a reserved segment of the site (for example `buscar`) is added to the catalogue
- **THEN** the check fails and points to the conflicting slug

#### Scenario: a composed slug with two readings

- **WHEN** the catalogue reaches a state in which the same composed slug can be read as two different trade and zone pairs
- **THEN** the check fails and names the two possible readings

### Requirement: Trades assignable to the business by the admin

The system MUST allow linking catalogue trades to a business (many-to-many relation). A newly registered business has no trades; the admin assigns it 1 to 3 on approval (PRD §6.3), and a business can be published without a trade if none fits (Appendix B). The 1-3 bound is enforced in the review panel, not in the database.

#### Scenario: trade assignment

- **WHEN** the admin links 3 trades to a business
- **THEN** the three links are persisted and queryable both from the business and from each trade

#### Scenario: newly registered business without trades

- **WHEN** a business is created from the registration
- **THEN** it has no trade linked

### Requirement: Review status, origin and lifecycle timestamps

The business MUST have a status with values `in_review | published | rejected` (default `in_review`), an origin with values `seeded | organic` (PRD §6.3 and §10; default `organic`, the admin adjusts it on approval), a registration timestamp assigned automatically on creation and a publication timestamp that stays null until the card is published. **The publication timestamp means "the last time the card was published": when it is unpublished it MUST NOT be erased —it is the only trace that it was in the directory and when—, and when it is published again it is overwritten with the date of the new publication. What decides whether a card is shown is its status, never that timestamp.** It MUST also store the rejection trace: a rejection timestamp and the reason as text, both null while the business has not been rejected. The rejection date is what enables the deletion of rejected registrations at 90 days required by PRD §8. If a rejected business corrects and resubmits its registration, both fields MUST go back to null, so that the purge does not take away a registration that is back in the queue. The demo business seed MUST populate both fields in its `rejected` business, so that the panel and the purge have a realistic case to test.

The sets of valid values MUST be enforced by the database, with hand-written constraints in the migrations, **in the production dialect**. Those constraints MUST still be present after applying the full migration tree, not just the first one: a later migration that drops them is a defect that the automatic check MUST detect.

#### Scenario: newly created business

- **WHEN** a business is created
- **THEN** its status is `in_review`, its registration timestamp has the creation date, and its publication timestamp, its rejection timestamp and its rejection reason are null

#### Scenario: publication

- **WHEN** a business moves to status `published` and is assigned the publication date
- **THEN** both values are persisted and queryable

#### Scenario: the publication date survives unpublishing

- **WHEN** a published business is unpublished and ends up in `in_review`
- **THEN** its publication timestamp still has the date on which it was published, and no public surface shows it because its status is no longer `published`

#### Scenario: republishing updates the publication date

- **WHEN** an unpublished card is published again
- **THEN** its publication timestamp holds the date of this publication, not the previous one

#### Scenario: rejection with date and reason

- **WHEN** a business moves to status `rejected` with the rejection date and the reason the admin wrote
- **THEN** both values are persisted and queryable, and the business still exists in the database (it is not deleted at that moment)

#### Scenario: the rejection trace is cleared on returning to review

- **WHEN** a rejected business returns to status `in_review`
- **THEN** its rejection timestamp and its reason are null again

#### Scenario: values outside the set

- **WHEN** an attempt is made to save a status or origin outside the defined values
- **THEN** the database rejects the write (CHECK constraint in the migration), in the same engine that runs in production

#### Scenario: the constraints survive the whole migration tree

- **WHEN** all migrations are applied in order on an empty database and then an attempt is made to save an invented status
- **THEN** the database rejects it: no later migration swept away the hand-written constraints

#### Scenario: the demo seed includes a rejection with a reason

- **WHEN** the demo business seed is run
- **THEN** its `rejected` business comes with the rejection date and reason populated, with a fictitious reason

### Requirement: The business stores the trace of its unpublishing

The business MUST store an unpublishing timestamp and the reason as text, both null as long as the card has never been unpublished. The two are written together when the admin unpublishes a published card (PRD §6.3 "se retiran, si ya estaban publicadas"; PRD §8 "las fichas retiradas a solicitud del negocio, de inmediato") and are overwritten on each later unpublishing: they always reflect the last one.

This trace is NOT cleared in any transition: it survives the card being published again, rejected or resubmitted by the business, because it is useful history inside the panel ("esta ficha ya la bajaste una vez, por esto") and no query depends on it being null. So that this old trace does not pollute the queue, **the wait of a registration is counted from the most recent of its registration date and its unpublishing date** (see `admin-review`), never from the unpublishing date alone.

The unpublishing reason is internal panel data, of the same kind as the rejection reason: it MUST NOT appear on any public page. These two fields MUST be born null when the full migration tree is applied, with no migration filling them or touching the CHECKs for `status` and `origin`.

#### Scenario: business that has never been unpublished

- **WHEN** a business is created and published
- **THEN** its unpublishing timestamp and its unpublishing reason are null

#### Scenario: unpublishing with date and reason

- **WHEN** a published business moves to `in_review` through an unpublishing, with its date and the reason the admin wrote
- **THEN** both values are persisted and queryable, and the business still exists with all its other data

#### Scenario: the trace reflects the last unpublishing

- **WHEN** a card is unpublished, published again and unpublished once more with a different reason
- **THEN** the date and the reason of the second unpublishing are stored, not those of the first

#### Scenario: the trace survives the other transitions

- **WHEN** an unpublished card is rejected, or published again
- **THEN** its unpublishing date and reason stay stored, neither erased nor altered

#### Scenario: the unpublishing trace is born null

- **WHEN** the full migration tree is applied and published, in-review and rejected businesses are written without touching these fields
- **THEN** both are null in all of them, no migration fills them and the CHECKs for `status` and `origin` are still in force

### Requirement: The zone allows "Otra" with free text pending normalization

The system MUST allow registering a business without a catalogue zone, storing the free text it entered (PRD §6.1, Appendix A). A business in that condition MUST be identifiable as pending normalization, and the admin MUST be able to normalize it by later assigning it a catalogue zone.

#### Scenario: registration with zone "Otra"

- **WHEN** a business registers with the option "Otra" and the text "Rinconada del Venado"
- **THEN** the free text is saved and the business has no catalogue zone assigned (pending normalization)

#### Scenario: normalization by the admin

- **WHEN** the admin assigns a catalogue zone to the business
- **THEN** the business is linked to that zone and is no longer pending normalization

### Requirement: The `Report` model stores a resident's notice about a card, with no data about the sender

The system MUST persist the reports from the "Reportar" button (PRD §6.3) in a table of their own, linked to the reported business, with exactly this data and nothing more: the business it points to, the reason, the optional comment, the status and the dates. Specifically:

- **Reason**: one from a closed list of four stable values (`closed`, `not_real`, `incorrect_data`, `inappropriate`), with the validation of the set enforced by the database (CHECK constraint hand-written in the migration, as is already done with the business status and origin, in the production dialect — ADR-004). The labels people see live in the code, not in the database: the stored value is stable even if the copy changes.
- **Comment**: optional text, null when the resident wrote nothing; the 300-character bound is enforced in the form, not in the database.
- **Status**: `pending | attended`, with default `pending` and a CHECK of the set.
- **Dates**: the creation date, assigned automatically, and the attention date, null until the admin marks the report as attended.

The table MUST NOT have any column that identifies who reported: no IP, no fingerprint, no name, no contact, nor a value derived from them (PRD §8 and LFPDPPP: what is not stored cannot leak).

The relation to the business MUST be declared **with cascade delete**, as the requirement "Permanent deletion of a business (ARCO operation)" demands: the notice of an anonymous resident cannot block or outlive the exercise of an ARCO right by the data subject, and the automatic check of the foreign keys that point to `Business` MUST also walk this relation, so that removing the cascade makes the check fail.

The system MUST be able to query, per business, how many reports it has in status `pending`, and list the pending reports of a business from oldest to newest. When the full migration tree is applied, the reports table MUST end up created and empty, without altering any column of `Business` and without dropping the CHECKs that already exist.

#### Scenario: newly created report

- **WHEN** a report is created on a published business with reason `closed` and no comment
- **THEN** it is saved with that business, that reason, null comment, status `pending`, creation date set and null attention date

#### Scenario: report with comment

- **WHEN** a report is created with a text comment
- **THEN** the comment is persisted exactly as it was sent and is retrievable unaltered

#### Scenario: reason outside the set

- **WHEN** an attempt is made to save a report with a reason that is not in the closed list
- **THEN** the database rejects the write (CHECK constraint of the migration)

#### Scenario: status outside the set

- **WHEN** an attempt is made to save a report with a status other than `pending` or `attended`
- **THEN** the database rejects the write

#### Scenario: attending a report

- **WHEN** a report moves to status `attended` with its attention date
- **THEN** both values are persisted and that report stops counting among the pending ones of its business

#### Scenario: count and list of pending reports per business

- **WHEN** a business has three pending reports and one already attended
- **THEN** its pending count is 3 and the pending list returns those three, from oldest to newest, without the attended one

#### Scenario: nothing about the reporter in the schema

- **WHEN** the columns of the reports table are reviewed
- **THEN** there is none that stores IP, name, contact or any other identifier of who reported

#### Scenario: the relation to the business is cascading

- **WHEN** the check of the schema relations that point to the business is run
- **THEN** the reports one appears among those checked and is declared with cascade delete; removing the cascade makes the check fail

#### Scenario: the reports table is born empty and does not touch the business

- **WHEN** the full migration tree is applied on an empty schema and a business is written
- **THEN** the reports table exists and is empty, the business keeps its columns as the model declares them and the CHECKs for status and origin are still in force

### Requirement: Permanent deletion of a business (ARCO operation)

The system MUST allow permanently deleting a business (a real hard delete, not unpublishing), **whatever status it is in** (`in_review`, `published` or `rejected`), deleting its row **and everything that hangs from it**: its links to trades, its reports, **all its edits —pending or already resolved—**, any other row linked to the business that the model may come to have and **the files of its photo in storage**, leaving no data or images recoverable by any query or by any address of the site (PRD §8). An edit stores the same personal data as the card (name, WhatsApp, phone, address), so a deletion that left it behind would not be a deletion. Deleting the business MUST also take its link fingerprint with it, so that no management link keeps resolving to anything. The deletion of the files MUST include all the generated variants: a file that survives the deletion is the personal data that the privacy notice promised to delete. If the file was no longer there (for example, because it was deleted earlier), the deletion of the business MUST complete anyway and MUST NOT fail. It is a different matter when storage **cannot be reached**: there the deletion is not executed and the row is not touched, according to the requirement "Permanent deletion refuses to claim it deleted what it did not delete" (`deployment`), which also fixes the order: files first, then the row.

**The cascade MUST be guaranteed by the model, not by the action that deletes**: every relation that points to the business is declared with cascade delete, so that a new table someone adds later cannot leave orphan rows or prevent an ARCO deletion. The project MUST have an automatic check that walks the relations declared in the database schema and fails if any that points to the business is not cascading, so that the invariant does not depend on someone remembering it. No data linked to a third party (for example the notice from a resident who reported the card) MUST be able to block the deletion: the data subject's ARCO rights weigh more.

The deletion MUST be idempotent: requesting the deletion of an identifier that no longer exists MUST NOT produce an error, but have no effect.

#### Scenario: hard delete

- **WHEN** a business that had trades linked and a photo is permanently deleted
- **THEN** its row, all its links to trades and all the variants of its photo disappear; no later query returns its data and the address that served its photo responds as if it had never existed

#### Scenario: hard delete of a business with reports

- **WHEN** a business that had pending and attended reports is permanently deleted
- **THEN** the deletion completes, its reports disappear with it and no later query returns either the business or its reports

#### Scenario: the deletion takes the edits with it

- **WHEN** a business that had one pending edit and two already resolved is permanently deleted
- **THEN** those three edits also disappear and no later query returns the name, the WhatsApp, the phone or the address they carried

#### Scenario: the link of a deleted business does not resolve

- **WHEN** the management link of a permanently deleted business is opened
- **THEN** it responds as not found, just like an invented link

#### Scenario: deleting in any status

- **WHEN** a `published` business, an `in_review` one and a `rejected` one are permanently deleted
- **THEN** all three disappear equally, regardless of their status

#### Scenario: deletion with the file already absent

- **WHEN** a business whose photo is no longer in storage is permanently deleted
- **THEN** the business is deleted anyway, without error

#### Scenario: idempotent deletion

- **WHEN** the deletion of the same identifier is requested twice
- **THEN** the second time no error occurs and there is nothing more to delete

#### Scenario: no relation blocks the deletion

- **WHEN** the check on the schema relations that point to the business is run
- **THEN** all are declared with cascade delete, and adding a new relation without cascade makes the check fail

### Requirement: Reproducible initial migration and seed

Superseded in v2 by Reproducible migrations that carry the reference data (v2) — source: ADR 0005, ADR 0006, ADR 0019.

The project MUST be able to bring up the database from scratch with the Prisma migrations and populate the catalogues with `npm run db:seed`. The seed MUST be idempotent. The database MUST be of the same engine in development, tests and production (PostgreSQL, ADR-004), with a single migration tree: the one applied on the laptop is the one applied at the provider. Bringing up the local database MUST require a single documented command, with no accounts or paid services.

#### Scenario: database from scratch

- **WHEN** the migrations are applied on an empty database and then `npm run db:seed` is run
- **THEN** the database ends up created with all the tables and the three catalogues populated (8 categories, 21 zones, 49 trades)

#### Scenario: idempotent seed

- **WHEN** `npm run db:seed` is run twice in a row
- **THEN** the catalogue counts do not change between the first and the second run

#### Scenario: the development database is the same as the production one

- **WHEN** someone brings up the local database with the documented command and applies the migrations
- **THEN** they get the same engine and the same schema as production, and the tests they run locally exercise the real dialect

### Requirement: The migration tree applies in full and its constraints survive

The migration tree MUST be able to be applied in full on an empty database with the same command used in production, and the resulting schema MUST contain all the tables of the model, with no differences from the declared schema. A row written with only the columns of the original model MUST end up with ALL later columns null: no migration MUST fill in data that nobody declared. The hand-written constraints MUST still be alive after applying the full tree, and no migration MUST drop them.

#### Scenario: the full tree on an empty database

- **WHEN** all migrations are applied in order on an empty schema
- **THEN** all the tables of the model are there and the schema does not differ from the declared one

#### Scenario: columns that arrived later are born null

- **WHEN** a row is written with only the columns of the original model
- **THEN** all the columns that were added later are null, and no migration fills them

#### Scenario: the hand-written constraints survive

- **WHEN** the full tree is applied and then an attempt is made to save a value outside the set
- **THEN** the database rejects it, and no migration in the tree contains a statement that drops those constraints

### Requirement: Rejected registrations are permanently deleted after 90 days

The system MUST permanently delete —the same real deletion as the ARCO operation, leaving no data recoverable by any query— the businesses in status `rejected` whose rejection date is 90 days old or more, which is the commitment published in the privacy notice (PRD §8). The purge MUST NOT touch any business in another status, nor a rejected one that has not yet reached the deadline, nor a rejected one without a rejection date. It MUST be idempotent: running it twice in a row leaves the database the same and does not fail. It MUST report how many registrations it deleted, without publishing any personal data in that report.

#### Scenario: rejected business that reached the deadline

- **WHEN** the purge runs and there is a rejected business with a rejection date of 90 days ago or more
- **THEN** that business disappears together with its links to trades, and no later query returns its data

#### Scenario: rejected business that has not yet reached the deadline

- **WHEN** the purge runs and there is a business rejected 89 days ago
- **THEN** that business stays in the database, intact

#### Scenario: the purge does not touch what is not its own

- **WHEN** the purge runs with published, in-review and recently rejected businesses in the database
- **THEN** only the rejected ones that reached the deadline disappear; the count of published and in-review ones does not change

#### Scenario: the business that corrected and went back to the queue

- **WHEN** a business was rejected more than 90 days ago but corrected and went back to `in_review` (its rejection date became null)
- **THEN** the purge does not delete it

#### Scenario: idempotent purge

- **WHEN** the purge runs twice in a row
- **THEN** the second deletes nothing, does not fail and reports it as zero

#### Scenario: the report does not leak personal data

- **WHEN** the purge finishes
- **THEN** what it reports and what it leaves in the log is a count, with no business names, WhatsApp numbers or rejection reasons

### Requirement: The purge reports what it could not purge

The purge of rejected registrations MUST keep going when it fails with one: an error with one card MUST NOT prevent the others from being purged. A stable failure with a single card would leave the privacy notice obligation unmet **forever**, with no signal other than a daily error.

It MUST report how many registrations were left unpurged, in addition to how many were deleted, and the HTTP trigger MUST respond with an error code when that number is not zero: a success with the bad news inside the body would be taken as good by the task scheduler. Like everything that comes out of the purge, what is reported MUST be counts, with no personal data.

#### Scenario: one card fails and the others are purged

- **WHEN** the purge runs and the photo store cannot be reached when deleting the photo of one of the registrations
- **THEN** that registration is NOT deleted —the row is not touched, because the files go first—, it is counted as not purged, the other registrations that reached the deadline are purged, and the HTTP trigger responds with an error

#### Scenario: a registration that cannot be deleted

- **WHEN** the purge fails to delete a registration that has reached the deadline
- **THEN** it counts it separately, continues with the others and the HTTP trigger responds with an error so that the task scheduler records it as a failure

### Requirement: The business stores its management link as a fingerprint, never in plain

The `Business` model MUST store the management link (PRD §6.4) as the **SHA-256 fingerprint of the token**, in an optional and unique field, plus the date it was generated. The plain token MUST NOT be persisted in any column, in any log or in any file of the project: the database has to be able to be backed up without the backup containing anyone's links. Both fields MUST stay null as long as the card has not been approved. Generating a new link MUST replace the previous fingerprint, so that the database never keeps more than one valid link per business. The migration MUST be able to be applied on a database that already has businesses, without losing or altering their data.

#### Scenario: newly registered business

- **WHEN** a business is created from the registration
- **THEN** its link fingerprint and its generation date are null

#### Scenario: the database does not store the token

- **WHEN** a management link is generated and then the business row is reviewed
- **THEN** what is stored is a fingerprint from which the token cannot be recovered, and the plain token does not appear in any column

#### Scenario: two businesses cannot share a fingerprint

- **WHEN** an attempt is made to save in a second business the same fingerprint that another already has
- **THEN** the database rejects the operation for violating the uniqueness constraint

#### Scenario: regenerating replaces

- **WHEN** a business that already had a link receives a new one
- **THEN** its row ends up with a single fingerprint —the new one— and with the generation date updated

#### Scenario: migration on a database with data

- **WHEN** the migration is applied on a database that already has published, in-review and rejected businesses
- **THEN** all the rows are still there with their data intact and the new fields are null in all of them

### Requirement: A pending edit stores the full content of what is to be published

The system MUST persist the edits a business sends in a table of their own, separate from `Business`, with **the full content** of what would be published if approved —the same fields the business can enter in the form— plus the business it belongs to, its status (`pending | applied | discarded`, with CHECK in the migration), the date it arrived, the date it was resolved and the discard reason. Saving an edit MUST NOT modify any column of the business.

The database MUST prevent a business from having two `pending` edits at the same time. The fields of an edit MUST NOT include the status, origin, trades, publication date, consent record or link fingerprint of the business: those are not editable and do not travel in an edit.

#### Scenario: edit saved without touching the card

### Requirement: The audit log records the destructive actions of the admin (v2)

Added in v2 — source: PRD §4, ADR 0010. Since EMR-48 the unpublishing and the permanent deletion of the panel write their entries (`admin-review`, "Unpublishing, a new link and the permanent deletion are forms of the detail, and their actions check everything again (v2)").

The card's status is preserved, so its actual status at the save is the entry's previous status.

The system MUST keep an audit log with one entry for each destructive or irreversible admin action: reject, unpublish, permanent deletion, purge, and edits to contact data. Nothing else MUST be logged. An entry MUST NOT depend on the card existing: deleting the card MUST NOT delete its entries. The entries of a permanent deletion or a purge MUST NOT contain personal data of the deleted business (name, WhatsApp, address, reasons).

### Requirement: A pending edit replaced by a newer one is kept as superseded (v2)

### Requirement: Panel users, roles and permissions live in the database (v2)

Added in v2 — source: ADR 0021, ADR 0010.

What they may do MUST come from roles stored in the database: a role bundles permissions from the catalogue and has a scope, `global` or `locality`, and a role assignment gives a role to a user, everywhere for a global role and in one locality for a locality role. The database MUST reject an assignment whose locality does not match its role's scope, the same role twice in the same place, the deletion of a role in use and a change of scope of a role in use.

The permission catalogue MUST be the same in the database and in the code that checks it; an automatic check MUST fail when they differ. The migrations MUST create the catalogue and two base roles: `super_admin` (global, holding every permission, including those added later) and `locality_admin` (per locality: review, edit, unpublish and delete cards, resolve pending edits, attend reports, generate links, manage zones and read the audit log). `super_admin` is a system role: it MUST NOT be updated, deleted or given permissions one by one. A user MAY do an action in a locality only when an active assignment that applies there grants its permission; an action that is not about one locality (users, roles, localities) needs a global assignment. An inactive user, or one without assignments, MAY do nothing. The first super admin of each environment is inserted by hand in the database; nothing about people lives in the repository or in its configuration.

The two operations serialize on the system role in one transaction and make the count guard part of their conditional write, so concurrent requests cannot both remove the last access. An inactive super admin does not satisfy the guard. Creating, deactivating, reactivating and assigning users and creating or editing roles write no audit entry: the log records the card actions in "The audit log records the destructive actions of the admin (v2)" alone.

### Requirement: The slugs of the catalogues do not produce ambiguous URLs at the root of a locality (v2)

Added in v2 — source: ADR 0006, ADR 0007. Amended on 2026-10-18 by EMR-52: the panel runs the same check before it saves a zone the admin adds. Amended on 2026-10-19 (EMR-73) by decision of the product owner: each deploy runs the check on the target database plus its pending migrations before applying them.

The pages of a locality live under `/{estado}/{municipio}/` (see "Public URLs carry the state and the municipality (v2)" in `public-directory`). There, one path segment is a category (`servicios-del-hogar`), a trade (`plomeria`) or a trade and a zone of that locality joined by a hyphen (`plomeria-haciendas-de-tizayuca`), next to the site's own pages, so every such segment MUST read in only one way. For each locality, with the global categories and trades and all the zones of that locality (hidden ones included, because a slug never changes), the project MUST have an automatic check that fails —before anything is published— when:

- a trade slug or a zone slug matches a category slug;
- a slug of the three catalogues, or a composed slug `«trade»-«zone»`, matches a reserved segment;
- a composed slug matches a category slug or a trade slug;
- two different trade and zone pairs produce the same composed slug.

A zone on its own is not a page, so a zone slug that matches a trade slug or a composed slug still reads in one way. The reserved segments are declared once, in the code the check and the routes share: the first segment of the other pages of a locality (`buscar`, `negocio`, `reportar`, `registro`, `editar`), the legal pages (`aviso-de-privacidad`, `terminos`) and the routes at the root of the site (`admin`, `health`). A new page of a locality adds its first segment there. The check names every conflicting segment with all its readings. It runs against the catalogues the migrations leave, so a migration that adds a category, a trade or the zones of a locality fails the tests when it makes a URL ambiguous. The panel runs the same check, with the same reserved segments, on the catalogues as they are plus a zone the admin is about to add, and refuses the zone when one of its readings conflicts (`admin-review`, "The admin can add a zone to a locality (v2)"); a rename never changes a slug, so it needs no check. Reserving a name is free; migrating an already published URL is not.

Because a zone the admin adds is data that no migration carries, the check also guards every deploy. Before `vp run db:migrate`, each deploy workflow runs `scripts/check-catalogue-urls.ts` with the environment's `DATABASE_URL`. The script opens a transaction on the target database, applies the pending migrations inside it, runs `rootUrlConflicts` on every locality with zones (one global check when there is none, so a category and a trade that clash never pass unnoticed), and rolls the transaction back. It stops the deploy, without applying the migrations, when it finds a conflict, naming each conflicting segment, its number of readings and the locality, and never a card's data. Everything, the pending migrations included, happens inside that transaction, so the check leaves the database unchanged whether it passes or fails, and a migration that cannot run inside a transaction fails the check and the deploy. The real migration runs only after the check passed.

#### Scenario: today's catalogues are unambiguous

- **WHEN** the check runs on the migrated database
- **THEN** it passes for every locality that has zones; for Tizayuca, with 8 categories, 49 trades and 105 zones

#### Scenario: a trade or a zone named like a category

- **WHEN** a trade, or a zone, whose slug matches that of a category is added to the catalogue
- **THEN** the check fails and names the slug, read as the category and as the trade or zone

#### Scenario: a slug that would shadow an own route

- **WHEN** a category, a trade or a zone whose slug is a reserved segment (for example `buscar`) is added to the catalogue
- **THEN** the check fails and points to the conflicting slug

#### Scenario: a composed slug that is already taken

- **WHEN** a trade and a zone compose the slug of a category, of a trade or of a reserved segment
- **THEN** the check fails and names the segment with both readings

#### Scenario: a composed slug with two readings

- **WHEN** the catalogue reaches a state in which the same composed slug can be read as two different trade and zone pairs
- **THEN** the check fails and names the two possible readings

#### Scenario: a zone named like a trade

- **WHEN** a zone whose slug matches that of a trade is added to a locality
- **THEN** the check passes: the segment can only be read as the trade

#### Scenario: a zone the admin added conflicts with a pending migration

- **WHEN** the deploy check applies the pending migrations on a target database that holds a zone the panel added, and a new category or trade takes that zone's slug or makes a composed slug read in two ways
- **THEN** the deploy stops before applying the migrations and names each conflicting segment, its number of readings and its locality

#### Scenario: the deploy check never changes the database

- **WHEN** the deploy check runs on a target database, whether it passes or fails
- **THEN** every pending migration it applied and every table or schema it created are rolled back, and the database keeps exactly what it had before

### Requirement: Seed of fictitious businesses for development (v2)

Added in v2 — source: ADR 0006, ADR 0008, decision of 2026-10-14. Amended on 2026-10-18 by EMR-35: the photos of "The demo seed leaves cards with a photo to see the directory as the resident will see it" arrive, as "The demo seed draws its photos and writes them where its environment serves media (v2)" describes.

`vp run db:seed` MUST fill the database with fake businesses, to see the directory working in development and in the deployed environments `dev` and `stage`; it never runs in `prod` (see "The commands that write in bulk read the environment from `ENVIRONMENT` (v2)" in `deployment`). It seeds nothing else: the reference data comes with the migrations ("Reproducible migrations that carry the reference data (v2)"), which create no business. The seed fills one locality, Tizayuca. It MUST be idempotent, because it runs on every deploy: it inserts only the fake businesses that are missing, recognized by their fixed identifier or by their WhatsApp in the locality, and it never changes a row that is already there.

The set MUST cover what the directory needs to test: published businesses in several categories (including "Clubes y escuelas deportivas") and several zones, some with home delivery and some without, some with all the optional fields and some with only the required ones, one published with zone "Otra" not normalized, one in `in_review` and one `rejected`. #### Scenario: the migrations create no business

- **THEN** the businesses table is empty

#### Scenario: idempotent seed

- **THEN** the second run inserts nothing and changes nothing, and no business ends up with repeated trades

#### Scenario: a business that is already there

#### Scenario: fictitious data and nothing real

### Requirement: The demo seed draws its photos and writes them where its environment serves media (v2)

- **THEN** the seed writes no photo for that fake business

### Requirement: The site's switches live in one row of the database (v2)

Added in v2 — source: ADR 0012; decision of the product owner, 2026-10-18 (EMR-42).

The switches of the whole site MUST live in the database, so an admin changes them without a deploy: one table, `site_settings`, with exactly one row, whose key `singleton` can only be true, and one typed column per switch, `NOT NULL` with the default the switch takes when its migration adds it. Today it holds one switch, `turnstile_enabled`, on (`business-registration`, "Turnstile is checked on the server, fails closed and has a switch in the database (v2)"); the migration that creates the table inserts the row. A later switch, such as the SMS verification flag (E6), is a new column with its default, in its own migration, and needs no new table. A switch is changed today with one SQL statement in the database of each environment (README, Operations), later from the panel (epic F). Code reads each switch through one function of the core; when the row is missing, which no migrated database allows on purpose, each switch takes its safe value: Turnstile on. A public page reads the switches through the cached `HYPERDRIVE`, so a change reaches it within a minute; an action that depends on one reads it through `HYPERDRIVE_FRESH`.

#### Scenario: the migrations

- **WHEN** the migrations are applied to an empty database
- **THEN** `site_settings` holds one row, with `turnstile_enabled` true

#### Scenario: one row

- **WHEN** a second row is inserted, with any key
- **THEN** the database rejects it

#### Scenario: no row

- **WHEN** the row is missing
- **THEN** Turnstile counts as on

### Requirement: The management link is issued by the panel alone and resolved by its fingerprint (v2)

Added in v2 — source: ADR 0010; EMR-43 and the decisions of the product owner of 2026-10-18; `admin-review`, "Approving a registration generates its management link, unique and unrepeatable" and "The admin can generate a new link, and the previous one stops working". It settles how "The business stores its management link as a fingerprint, never in plain" is written and read.

A token is 32 bytes from a cryptographic random source (256 bits), written in base64url without padding: 43 characters of `A-Za-z0-9_-`, which travel in an address as they are and derive from nothing about the business. The business stores the SHA-256 of the token's UTF-8 bytes, in lowercase hexadecimal, and the moment the link was generated, with no salt and no slow key derivation: those protect secrets of low entropy, and 256 random bits have none to guess.

Issuing a link writes the fingerprint of a new token and its moment at once, replacing any earlier link, and gives back the token, the only time it exists in plain. It happens only to a published card: a card that is not published gets no link and nothing changes, so a card that was never approved has none. Only the panel issues a link (`admin-review`, on approving, in the same transaction that publishes the card, and on "Generar un enlace nuevo", epic F): no page, action, script, seed or SQL statement of the repository issues one, and the tests issue theirs the way the panel does. Issuing can join the transaction of an approval, so an approval that fails leaves no link.

Resolving a token looks it up by its fingerprint, always, whatever arrived, in one query for a published card of the given locality with that fingerprint, and compares the fingerprint found with the one computed in constant time (`business-registration`, "The edit mode of a locality lives under it, and lands on its confirmation (v2)"). A token, whole or in part, and its fingerprint MUST NOT be written to the log or to any file, and the token to no column.

#### Scenario: a token

- **WHEN** the server generates tokens
- **THEN** each is 43 characters of base64url that decode to 32 random bytes, no two are the same, and the business stores the SHA-256 of each in hexadecimal

#### Scenario: issuing a link

- **WHEN** a link is issued for a published card
- **THEN** the card stores its fingerprint and the moment, the token appears in no column, and the token opens the card's edit mode

#### Scenario: a card that is not published

- **WHEN** a link is asked for a card in review, a rejected card or an identifier no card has
- **THEN** no link is issued and nothing changes

#### Scenario: regenerating

- **WHEN** a second link is issued for the same card
- **THEN** the card keeps only the new fingerprint, with its moment, and the first token opens nothing from then on

#### Scenario: resolving

- **WHEN** a token is resolved in a locality, whether it opens a card or not
- **THEN** one query runs, by its fingerprint, and only a published card of that locality with exactly that fingerprint is found

### Requirement: A pending edit may change the photo of its card (v2)

Added in v2 — source: decision of the product owner, 2026-10-18 (EMR-43); ADR 0011; `business-registration`, "The edit of a card may change its photo, which reaches the card only when the edit is applied (v2)". It amends "A pending edit stores the full content of what is to be published": the full content includes what the edit asks of the photo. Amended on 2026-10-18 by EMR-49: what applying and discarding leave on the edit.

A pending edit MUST record what it asks of the card's photo: `keep`, which leaves it and is what every edit saved before this asks; `replace`, which puts in its place the new photo the edit uploaded; or `remove`, which leaves the card without one; any other value is refused by a CHECK in the migration. Only an edit that asks `replace` MAY carry the key of a new photo, and one waiting for review always does: a key of the shape of "A photo key is 24 characters of the identifier alphabet, and names two objects under `photos/` (v2)", which the server generates, and that no other edit names, so one edit names a photo at a time. The edit never copies the card's own photo key. While the edit waits, its new photo lives in the public media bucket under that key, which no public page names. Superseding an edit takes its key off it, in the same transaction: the newer edit takes the photo over when it keeps the photo, and otherwise its objects are deleted once the newer edit is saved; the superseded edit still says it asked `replace`.

A photo key that a waiting edit names is not an orphan: the orphan sweep MUST keep its objects. Whoever resolves an edit deals with its photo: applying a `replace` makes it the card's photo, so the photo of an applied edit is its card's, and the applied edit keeps naming its key; discarding an edit takes its key off it in the same write, as superseding does, while it still says it asked `replace`, and deletes that photo's objects once it is saved (`admin-review`, "Applying or discarding a pending edit carries out what it asks of the photo (v2)"); superseding one gives it to the newer edit or deletes it (`business-registration`). The permanent deletion of a business deletes the new photos of its edits with the photo of the card, photos first, then the rows.

#### Scenario: an edit with a new photo

- **WHEN** an edit is saved with a new photo
- **THEN** its row says `replace` and names the key of that photo, whose two objects are in the bucket, and the card's row does not change

#### Scenario: what an edit asks of the photo

- **WHEN** an edit is saved asking anything other than `keep`, `replace` or `remove`, a waiting `replace` without a key, a key without `replace`, a key of another shape, or the key another edit names
- **THEN** the database rejects the write

#### Scenario: a photo taken over

- **WHEN** a newer edit that keeps the photo supersedes an edit that carried a new photo
- **THEN** the newer edit names that key, the superseded one names none and still says `replace`, and the objects of the photo stay

#### Scenario: the orphan sweep and a waiting edit

- **WHEN** the orphan sweep finds the objects of a photo that only a waiting edit names
- **THEN** it keeps them

### Requirement: The business keeps the rejection its resubmission answered (v2)

Added in v2 — source: decision of the product owner, 2026-10-18 (EMR-47): the queue labels a resubmitted card "Reenvío" and its detail says why it was rejected before (`admin-review`, "The queue labels the resubmission of a rejected card, and its detail says why it was rejected before (v2)"). It amends "Review status, origin and lifecycle timestamps", whose rejection trace goes back to null on a resubmission and is lost.

The business MUST store a previous rejection: its moment and its reason as text, written together, both null while the card was never resubmitted after a rejection (a CHECK in the migration). When a rejected card is resubmitted, the same write that sets its rejection trace to null MUST copy that trace into the previous rejection, overwriting the one it held; a rejection without its moment leaves the earlier previous rejection as it was. Nothing else writes or clears it: approving, rejecting again, unpublishing and applying an edit keep it, so it always holds the rejection the last resubmission answered. The 90-day purge of rejected registrations reads only the rejection trace, never the previous rejection, so a card back in review is never purged for it.

The previous rejection is internal data of the panel, of the same kind as the rejection reason: it MUST NOT appear on any public page, and it leaves the database only with its card, whose permanent deletion takes it. The migration that adds it MUST be additive: two nullable columns that every existing row meets.

#### Scenario: a resubmission keeps the rejection

- **WHEN** a business rejected with the reason "La foto tenía personas" corrects and resubmits its registration
- **THEN** its rejection timestamp and reason are null, and its previous rejection holds that moment and "La foto tenía personas"

#### Scenario: the last resubmission wins

- **WHEN** that card is rejected again with another reason and resubmitted again
- **THEN** its previous rejection holds the second rejection

#### Scenario: written in pairs

- **WHEN** a previous rejection is saved with a moment and no reason, or a reason and no moment
- **THEN** the database rejects the write

### Requirement: The photo addresses waiting for their purge are the only thing kept of a deleted photo (v2)

Added in v2 — source: decision of the product owner, 2026-10-18 (EMR-48): a deleted photo is purged from the cache of the media hostname, and a purge that fails is retried without needing the card (`deployment`, "A deleted photo is purged from the cache of the media hostname, and a purge that fails is retried every hour (v2)"). It completes "Permanent deletion of a business (ARCO operation)", whose deletion of the files "leaving no data or images recoverable by any address of the site" now includes the cached copies, and whose files include the new photos of the card's edits, whatever their status.

When the purge of a deleted photo fails, the database MUST keep, in `photo_cache_purges`, the two addresses of that photo on the media hostname and the moment they were kept, and nothing else: no key of a card, no identifier, no name, no number, no locality. A CHECK in the migration MUST admit only an https address of a variant of a photo, `https://<host>/photos/<photo key>/card.webp` or `full.webp`, so the table can hold nothing about a business. An address is kept once, however many times its purge fails. The table points to no other table and no table points to it: a permanent deletion never waits on it, the purges never depend on the card existing, and the cascade check of "Permanent deletion of a business (ARCO operation)" is unchanged. The hourly retry deletes each address once Cloudflare has purged it. The photo's objects are already gone from R2 when its addresses are kept: only a cached copy may remain.

#### Scenario: a failed purge

- **WHEN** a photo is deleted and the purge of its addresses fails
- **THEN** `photo_cache_purges` holds exactly its two addresses, each with the moment it was kept, and no other column

#### Scenario: nothing but addresses

- **WHEN** a business name, a number, an http address or the address of anything but a variant of a photo is written to `photo_cache_purges`
- **THEN** the database rejects the write

#### Scenario: purged and forgotten

- **WHEN** the hourly retry purges the addresses that waited
- **THEN** they are no longer in the table

### Requirement: The orphan-photo sweep keeps only the state needed to resume (v2)

Added in v2 — source: ADR 0011, ADR 0013; EMR-57.

The database MUST have one row in `orphan_photo_sweep_state`, keyed by a `singleton` value that can only be true. The row stores only the opaque R2 listing cursor and the UTC day the last complete sweep finished; both are nullable, and the migration MUST insert the row. A cursor is written only after its whole page is handled, so a failed page remains the next page retried; a page left half-done by a bound of the run is listed again, since what was deleted is gone from it. Completing a pass clears the cursor and records the UTC day; a later hourly run skips another pass that day. The row has no relation to a business and no card data. Its cursor MUST NOT appear in logs or reports.

#### Scenario: the operational row exists

- **WHEN** all migrations are applied to an empty database
- **THEN** `orphan_photo_sweep_state` has exactly one row with `singleton = true`, a null cursor and a null completed day

#### Scenario: a partial sweep resumes

- **WHEN** a bounded run completes one page but has more objects to list
- **THEN** the next run starts from that page's R2 cursor

#### Scenario: a failed page is retried

- **WHEN** a page cannot be listed or one of its photos cannot be looked up or deleted
- **THEN** its cursor is not advanced, and the next hourly run tries the page again

#### Scenario: a completed day is idempotent

- **WHEN** the full pass completes and the task runs again on the same UTC day
- **THEN** it lists no objects and changes nothing
