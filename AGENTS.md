# enmirumbo

Hyperlocal business directory: Astro in server mode on Cloudflare Workers, built with Vite+. [README.md](README.md) explains how to run it.

- Product intent: [docs/PRD.md](docs/PRD.md).
- Behaviour: [docs/specs/](docs/specs/). When the PRD and a specification disagree, the specification wins on behaviour.
- Decisions: [docs/adr/](docs/adr/).

## Commands (Vite+)

- `vp install`: install dependencies. Its `prepare` script runs `vp config`, which installs the pre-commit hook (`vp staged`).
- `vp check`: format (Oxfmt), lint (Oxlint) and type check.
- `vp run check:all`: `vp check`, Prettier on `.astro` files, `astro check`, and `wrangler types --check`. Run it before opening a pull request.
- `vp test`: tests inside workerd with `@cloudflare/vitest-plugin`.
- `vp run db:up`, `db:down`, `db:generate`, `db:migrate`, `db:seed`, `db:check`: the local PostgreSQL 18 (Docker), Drizzle migrations, the seed and the migration guard. `vp test` needs the database up.
- `vp run e2e`: build, then run Playwright against `astro preview`. Its global setup migrates and seeds `DATABASE_URL` (default: the development database), which turns Tizayuca on, and writes the seed's photos to the local media bucket. Run `vp exec playwright install chromium` once first.
- `vp run dev`, `vp run build`, `vp run preview`: Astro's dev server, build and preview. Never use `vp dev`, `vp build` or `vp preview`: they run plain Vite, which ignores Astro.
- `vp run fmt:astro`: format `.astro` files with Prettier.
- `vp run types`: regenerate `worker-configuration.d.ts` after a change to `wrangler.jsonc`, and commit it.

Vite+ documentation is in `node_modules/vite-plus/docs`.

When Astro detects a coding agent, `astro dev` and `astro preview` start in the background. Stop them with `vp exec astro dev stop` or `vp exec astro preview stop`.

## Layout

- `src/worker.ts`: the Worker entry. `fetch` goes to Astro (locally, `/_media/` first serves the local media bucket, `src/lib/media.ts`), adds the security headers (`src/lib/security-headers.ts`), the headers of the edit mode (`src/lib/edit-mode.ts`) and, outside local, `X-Robots-Tag: noindex` (`src/lib/robots.ts`); `scheduled` runs the hourly jobs in `src/scheduled.ts`: every task of `SCHEDULED_TASKS`, at the scheduled time, each deciding by the local day or hour of each locality, idempotent, and logging counts only. It also exports the `QuotaCounter` Durable Object of the per-IP quotas (`src/lib/quota/`), and so does `test/worker/entry.ts`. Static assets skip the Worker: the build gives them the same headers through `_headers` (`src/integrations/static-headers.ts`).
- `src/middleware.ts`: Astro middleware. It sends every request for `/admin` and below, and every admin action, through the Cloudflare Access check in `src/lib/access/`; then it resolves the active locality of every page under `/{estado}/{municipio}/` (`src/lib/locality.ts`), or answers 404.
- `src/actions/index.ts`: the Astro Actions, every mutation of the site. Astro runs an action before the page its form posts to, and the page reads its result.
- `src/pages/`: Astro routes. Every page renders inside `src/layouts/BaseLayout.astro`, which reads the locality from `Astro.locals`, writes the metadata (canonical, Open Graph, share image) and the Umami script where it applies, and adds the header and footer (`src/components/`). `/robots.txt` and `/sitemap.xml` (`src/core/seo/sitemap.ts`) are routes too. `src/pages/admin/` holds the panel: the review queue (`/admin`), "Todos los negocios" (`/admin/negocios`), the audit log (`/admin/bitacora`, read-only, `src/core/review/audit-log.ts`), the details of a card (`/admin/registros/<id>`, where its approval, rejection, unpublishing, new link and the attention of its reports are posted, `/admin/registros/<id>/rechazado` and `/admin/registros/<id>/despublicado`, the confirmations of a rejection and of an unpublishing, and `/admin/registros/<id>/borrar`, the confirmation of a permanent deletion, where the deletion is posted, which lands on `/admin/borrado`, an address that names no card) and direct rectification (`/admin/registros/<id>/editar`, its save landing on `/admin/registros/<id>/editado`) and of a pending edit (`/admin/ediciones/<n>`, where it is applied or discarded, and `/admin/ediciones/<n>/aplicada` and `/descartada`, their confirmations), rendered by `src/components/admin/` from the queries and decisions of `src/core/review/`, the zones of a locality (`/admin/colonias`, `src/core/zones/`), and panel users and roles (`/admin/usuarios`, `/admin/roles`, `src/core/access/manage.ts`); the layout makes every page under `/admin` `noindex, nofollow` with the panel's referrer policy and no analytics, by where it lives.
- `src/styles/global.css`: the design tokens (Tailwind 4). Tailwind's default palette is off: use only the tokens; `test/scripts/design-tokens.test.ts` checks them and their contrast.
- `src/core/`: business rules and data access. It never imports `astro` or `astro:*` (an Oxlint rule enforces it). `src/core/db/` holds the Drizzle client (`withDb`), the schema and the seed; `src/core/legal/` the texts of the legal pages and the version of the privacy notice; `src/core/photos/` the photo key, the objects of a photo, the upload (`storePhoto`), the deletion of a photo (`deletePhoto`, `removePhoto`) and the purge of its addresses from the media hostname's cache (`cache.ts`); `src/core/management-link/` the token of a management link and the only code that issues and resolves one; `src/core/edit/` the edit mode of that link; `src/core/zones/` the zones screen of the panel, which hides, shows, renames and adds the zones of a locality.
- `drizzle/`: generated migrations and Drizzle Kit's journal. `scripts/`: Node scripts for the database tasks.
- `.github/workflows/deploy-*.yml` and `scripts/deploy/`: the deploys to `dev`, `stage` and `prod` (README, Deployment). `monitor.yml`, `backup.yml`, `scripts/monitor/` and `scripts/backup/`: the availability check and the nightly backup of production (README, Operations). The shell scripts are tested in `test/scripts/deploy-scripts.test.ts` and `test/scripts/operations-scripts.test.ts` and pass ShellCheck.
- `test/worker/`: Vitest tests inside workerd. They load `test/worker/entry.ts` instead of `src/worker.ts`, because Astro's handler only resolves inside an Astro build.
- `test/astro/`: Vitest tests that render Astro components with the Container API, in Node.
- `test/e2e/`: Playwright tests. Those in `test/e2e/search-pages/` run alone after the rest, because they add published cards to Tizayuca that the sitemap would list; `test/e2e/registration.spec.ts` and `test/e2e/edit.spec.ts` run alone after them, because they turn Turnstile's switch off for a while; `test/e2e/admin.spec.ts` runs alone after them, because it adds cards to Tizayuca and narrows the roles of the panel's local identity for a while (`test/e2e/local-admin.ts`, which the global setup uses to make it a super admin); `test/e2e/admin-users.spec.ts` runs alone after the other panel tests because it narrows the same local identity to the roles of a user it adds; those in `test/e2e/two-localities/` run after them, with a second, fictitious active locality. `test/e2e/surfaces.spec.ts` crawls the site and checks every page it reaches against the layout rules.
- `worker-configuration.d.ts`: generated by `wrangler types`. Never edit it by hand.

## Rules

- Code, comments, documentation, commit messages, pull requests and Plane work items are in English. UI copy is in colloquial Mexican Spanish ("Registra tu negocio gratis", never "Crear listado").
- The brand is enmirumbo, one word, always lowercase. Never write "enmirumbo Tizayuca". Texts that name a locality read it from the locality record; never hard-code a locality name.
- The public site works without JavaScript. Only the registration and edit forms need it, and only while Turnstile's switch is on: then the form's submit button is `disabled` in the markup, a `<noscript>` above its fields says why, and the widget's script enables the button once it has a token; with the switch off they submit and validate on the server without it. Every check stays on the server either way. No React or other client framework; mutations use Astro Actions with `accept: 'form'`.
- Turnstile (ADR 0012): a form that needs it (the registration, and the edit form) renders `src/components/TurnstileWidget.astro` with `turnstileSiteKey(env)` and its own action from `TURNSTILE_ACTIONS` while the switch is on, and its core calls `checkTurnstile` (`src/core/turnstile/check.ts`) after the trap field and before anything else, with the connection of the action (`HYPERDRIVE_FRESH`) and `turnstileVerifier(env)` (`src/lib/turnstile.ts`). Never send the visitor's address to siteverify. The switch is `turnstile_enabled` in the one row of `site_settings`, read with `isTurnstileEnabled` (`src/core/settings/settings.ts`); a new switch is a new column there. Test keys count only with `ENVIRONMENT` `local`; never accept a dummy token anywhere else, and never commit a test key for a deployed environment. The report form and the search never include Turnstile. The end-to-end tests that open a page with the widget import `test` from `test/e2e/turnstile.ts`, which answers Cloudflare's origin with a local fake.
- A public form posts to its own page with its action (`method="post"`, `action={actions.<name>.queryString}`). The action checks that it was posted from its page (`context.routePattern`) and answers not found otherwise; what the page is about, such as a card, it reads from the page's address (`context.params`, as `reportTarget` in `src/lib/report.ts` does), never from a field. The page reads the result with `Astro.getActionResult`: a success answers a 303 to a page of its own (`seeOther`, `src/lib/locality.ts`), so a reload never sends the form again; an error renders the form again from the same submission. What a person wrote never goes in a cookie or an address: the privacy notice lists exactly two cookies. The trap field of a public form is `src/components/HoneypotField.astro`, checked with `isHoneypotFilled` (`src/core/forms/honeypot.ts`). No public form relies on the browser's validation: the server checks every field and shows each error next to it, in Spanish (a form with typed or required fields is `novalidate`, as the registration's is).
- Mobile first: design for a 390 px wide phone.
- Every public page of a locality lives under `src/pages/[state]/[municipality]/` and reads its locality with `requireLocality(Astro.locals)`; the middleware has already answered 404 for an unknown or inactive one (ADR 0007). Build internal links with `localityPath` (`src/core/locality/paths.ts`), and a card's with `cardPath` (`src/core/business/card-path.ts`), never as literal paths, and absolute URLs with `absoluteUrl` (`src/lib/site-url.ts`), which reads `SITE_URL`. A public page shows a catalogue zone by its display name, read with `localityZoneNames` and applied with `withZoneName` (`src/core/catalogue/zone-names.ts`), never by its stored name, which can repeat. Every public list of businesses renders `src/components/ListingCard.astro` and shows `PAGE_SIZE` cards a page with `parsePage` and `pageSlice` (`src/core/pagination.ts`) and `src/components/MoreLink.astro`: `?pagina=n` from 2 on, and any other `pagina` or a page past the last answers 404. The panel's "Todos los negocios" follows its own specification instead (admin-review): 25 rows a page, "Página n de m", "Ver más antiguos" and "Ver más nuevos", and a `pagina` that cannot be read is page 1 (`src/core/review/businesses.ts`).
- An indexable page passes its own path as `canonicalPath` to `BaseLayout`, which declares its absolute canonical URL and `og:url`; a 404 or the panel passes none, and a page that answers but must not be indexed passes `noindex`. An indexable page of a locality also adds its kind to `LOCALITY_PAGES` (`src/core/seo/sitemap.ts`), the only list the sitemap reads; `test/e2e/seo.spec.ts` fails when a URL of the sitemap does not answer 200. A page of a locality that crawlers do not need goes in `LOCALITY_DISALLOW` (`src/lib/robots.ts`); never list the edit mode there.
- The share image of a locality is one static 1200×630 PNG at `src/assets/share/{estado}/{municipio}.png`, made as the README says; no code names it, and no generator script is kept.
- The content security policy (`src/lib/security-headers.ts`, `docs/specs/deployment.md`) allows no inline script or style and no external origin but Turnstile's, Umami's (production with a Website ID) and the media hostname (`MEDIA_URL`): never add a `style` attribute, an `is:inline` script or a resource from another origin. The only `<script>` tags a page writes itself are the Schema.org data block of `src/components/JsonLd.astro`, which browsers never run, and the processed `<script>`s of `src/components/RegistrationForm.astro` and `src/components/TurnstileWidget.astro`, which Astro bundles as files under `/_astro/` (`assetsInlineLimit: 0` keeps them from being inlined); `test/e2e/surfaces.spec.ts` allows them on the registration page alone, with the request of the widget's script to Turnstile's `api.js`, and `test/e2e/edit.spec.ts` on the edit page, which no crawl reaches. The panel rectification page (`/admin/registros/<id>/editar`) reuses only the processed `RegistrationForm.astro` script for its postal-code select, offer example and sending state; `surfaces.spec.ts` permits that one file there, with no Turnstile. A new origin changes the policy, its tests and the spec in the same pull request.
- Analytics (ADR 0014): only production with `UMAMI_WEBSITE_ID` loads Umami, never the panel or the edit mode (`isMeasured`, `src/lib/analytics.ts`). Events use only the names of `ANALYTICS_EVENTS` (the two WhatsApp buttons), declared with `eventAttributes`, whose only properties are the locality and the category slug; never put text a person typed in them. The registration has no event: its funnel is the page views of its form and its thank-you page, so its form, button and thank-you page carry no event attribute and no script to measure. A page view may carry one of `ANALYTICS_TAGS`, passed to `BaseLayout` as `analyticsTag`. A page that must not be indexed passes `noindex` to `BaseLayout`, and a title with no text a person typed.
- Per-IP quotas (ADR 0012): a page or an action asks with `takeQuota(env, request.headers, "<purpose>")` (`src/lib/quota/quota.ts`), the purpose written as a literal, and gives up when it is not allowed; each purpose has its own limit and window in `QUOTAS` (`src/core/quota/quotas.ts`), at most an hour, and the purposes are that fixed list, never built from a request. The counters and the key of their codes live in the memory of one single `QuotaCounter` Durable Object for every purpose, named `QUOTA_COUNTER_NAME`; the purpose is part of each counter's code, so each purpose counts apart. Never write an address or its code to its storage, the database or a log, or the privacy notice stops being true. The address is `CF-Connecting-IP`; tests send one from the ranges reserved for documentation (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`), since a loopback address is not counted.
- The quota counter must never run up a bill (ADR 0012, amended on 2026-10-15): reach `QUOTA_COUNTER` only as `getByName(QUOTA_COUNTER_NAME)`, never a Durable Object per visitor, address, user or purpose; the counter never uses `ctx.storage` and sets no alarm (`setAlarm`, `alarm()`); its one timer exists only while at least one counter exists, each arming is at most `MAX_TIMER_MS` ahead (under the 15 minutes for which a pending timer keeps an object in memory), and it is never set again once no counter remains; and `preview_urls` stays `false` at the top level and in every environment of `wrangler.jsonc`. `test/scripts/quota-guardrails.test.ts` and `test/worker/quota.test.ts` check them.
- Photos (ADR 0011): a page renders a photo only with the address `src/lib/media.ts` builds from `MEDIA_URL` and a stored key, never from a stored value as it is. A public page renders only the key of a published card, with `businessPhoto`, and never reads a key of an unpublished one. The admin panel may render the key of any card or pending edit it reviews, in review, rejected or unpublished included, with `panelPhoto`, which only pages under `/admin` call (admin-review, "The panel shows the photos it reviews from the media hostname (v2)"). The listing card shows the `card` variant, the card the `full` one (`src/core/photos/photo.ts`). Whatever writes a photo writes both variants under `photos/<key>/`, with `PHOTO_CACHE_CONTROL`. An uploaded photo goes only through `storePhoto` (`src/core/photos/upload.ts`), after every other check of its form, and never stays stored when its form is not saved; whatever stops naming a photo deletes its objects after the save. A photo is deleted only through `deletePhoto` or `removePhoto`, with the bucket `mediaBucket(env)` builds (`src/lib/media-bucket.ts`), never `env.MEDIA` alone (the types refuse it): they delete both objects and then purge both of its addresses from Cloudflare's cache of the media hostname, where they would be served for a year (deployment, "A deleted photo is purged from the cache of the media hostname, and a purge that fails is retried every hour (v2)"). A purge that fails keeps only those two addresses in `photo_cache_purges`, which the hourly task `photo-cache-purge` retries; nothing about a card ever goes there. The purge token (`MEDIA_CACHE_PURGE_TOKEN`) never goes in a log, an error or a page, and locally nothing is purged. The Images binding (`IMAGES`) is never declared with `remote`, so local runs and tests spend none of its monthly allowance. The public media bucket holds only public content, by prefix; anything private gets a bucket of its own. No image file goes in the repository but the share images: the seed draws its photos when it runs.
- Management links (business-registration, the edit requirements; data-model, "The management link is issued by the panel alone and resolved by its fingerprint (v2)"): only `issueManagementLink` (`src/core/management-link/link.ts`) issues a link, and only the panel calls it: the approval of a registration (`src/core/review/approval.ts`) and "Generar un enlace nuevo" (`src/core/review/new-link.ts`); no page, other action, script, seed or SQL issues one, tests issue theirs through it, and `test/scripts/management-link-guard.test.ts` names any other caller. The database keeps only the token's fingerprint. A token, whole or in part, or its fingerprint never goes in a log, a file, a cookie, an address, the message of an error or a page other than the edit page at its own address and the confirmation of the decision that issued it, which shows it once, in the answer to that decision's own submission and never behind a redirect (admin-review, "The management link is shown only in the answer to the approval (v2)"). A link is resolved only with `resolveManagementLink`, by its fingerprint.
- Everything at `/{estado}/{municipio}/editar/` and below is the edit mode, by where it lives (`isEditModeRequest`, `src/lib/edit-mode.ts`): `Referrer-Policy: strict-origin`, `noindex, nofollow`, `no-store` and no measurement on every response of it, a 404 included. Its pages link to nothing outside the site and to no address with a token, no public page links to it, and robots never names it.
- Public URLs always carry the state and the municipality: no route takes a single segment, so there is no short alias (`test/scripts/internal-links.test.ts` checks it). The visitor's approximate location (`Astro.request.cf`) is only a suggestion: never redirect by it, store it or log it. A redirect that depends on the visitor, such as the one the locality cookie makes, is a 302 with `Cache-Control: no-store`, never a 301.
- Business rules and data access live in `src/core/`, which never imports Astro. Pages and Actions validate input, authorize the request and call the core (ADR 0019).
- Read bindings with `import { env } from "cloudflare:workers"`. Astro sessions stay off.
- `wrangler.jsonc`: the top level is the local Worker; `dev`, `stage` and `prod` each declare their own bindings, vars and triggers, because Wrangler does not inherit bindings or vars. A new binding or variable goes in the top level and in the three environments (`test/scripts/wrangler-config.test.ts` checks it); then run `vp run types`. Build for an environment with `CLOUDFLARE_ENV=<env> vp run build`. Workers Logs and traces stay off at the top level and in every environment, each block writing `observability` with every key `false` (deployment, "Workers Logs and traces stay off in every environment (v2)"; `test/scripts/wrangler-config.test.ts` and `scripts/deploy/check-build.sh` check it): never turn them on there or in the dashboard, since an invocation log keeps each request's URL; debug with `wrangler tail`. Never run `wrangler deploy` by hand: the deploy workflows are the only way to deploy.
- The application runs natively; only supporting services, such as PostgreSQL, run in containers through Docker Compose (ADR 0019).
- Migrations are additive only: never edit an applied migration, and never drop, rename, retype, make `NOT NULL` or truncate in the same version that stops using a column or table. The destructive change comes one version later, in its own pull request, with `-- destructive-ok: <reason>` in the SQL file; `vp run db:check` fails without it.
- The database generates `name_normalized` and `what_you_offer_normalized` with the SQL function `search_normalize`; no code writes them. The search normalizes what a resident types with `normalizeText` (`src/core/search/normalize.ts`), which must give the same text as `search_normalize`; `test/worker/search.test.ts` compares them.
- Use `HYPERDRIVE` (cached, 60 seconds, not invalidated by writes) only for public reads; the specs allow a public page to show a change up to a minute late, and the panel says so. Use `HYPERDRIVE_FRESH` for writes, the admin panel, verification flows and any read that follows a write. Get a database through `withDb`; never create a `pg` client by hand.
- A `DATABASE_URL` that leaves the machine must use `sslmode=verify-full`. Seeds hold fictional data, use `.onConflictDoNothing()` and never run against `prod`. Phone numbers in seeds, tests and examples follow `771999xxxx`.
- A schema change in `src/core/db/schema/` comes with its migration (`vp run db:generate`); `test/scripts/schema-drift.test.ts` fails otherwise. Every foreign key to `businesses` is `ON DELETE CASCADE`, so a permanent deletion (ARCO) leaves nothing behind; `test/worker/data-model.test.ts` checks it. A new business gets its identifier from `newBusinessId()` (`src/core/business/id.ts`).
- Reference data (categories, trades, and the state, municipality, locality and zones of each city the directory serves, today only Tizayuca, its zones from SEPOMEX) ships in data migrations; `vp run db:seed` only adds fictitious businesses. A new city ships its reference data in its own data migration. A zone the admin adds from the panel (`/admin/colonias`, `src/core/zones/`) is not reference data but data the panel writes, like a card: no migration or seed carries it. Every zone has its postal code (SEPOMEX's for Tizayuca's, `drizzle/0016_zone_postal_codes.sql`; a zone the admin adds needs one), which the registration and edit forms group and narrow their zones by; the postal code a business types is stored with its card and shown only in the panel, never on a public page. Its slug comes from its name with `slugOf` (`src/core/catalogue/slug.ts`), the slug rule of every catalogue, and never changes, not even on a rename. Tests create any other state or municipality they need, fictitious and with a state code above 32 (`test/worker/fixtures.ts`), and remove it; they add zones only to those, never to Tizayuca, unless they run alone and give its zones back. A new page of a locality adds its first path segment to `RESERVED_SEGMENTS` (`src/core/catalogue/root-urls.ts`); `test/worker/root-urls.test.ts` fails when a slug of the catalogues takes a reserved segment or makes a URL of a locality read in two ways, and the panel refuses a new zone with the same check at runtime (`urlConflict`, `src/core/zones/rules.ts`, which calls `rootUrlConflicts`): never write a second copy of it.
- User and role management (`src/core/access/manage.ts`) checks global `users.manage` or `roles.manage` with `can(..., null)`. Targets come from the page address; both deactivation and assignment removal lock the system role and condition their write on preserving the last active super admin. No card audit entry is written. `/admin` uses `panelHome` for an active assigned user with no queue permissions; new implemented sections add their permission-filtered entry there.
- Admin authorization (ADR 0021): Access proves the email, the database decides what it may do. Check a permission with `can()` (`src/core/access/queries.ts`) in the locality of what the action touches; never check a role by name. A screen that lists several localities reads where the user holds each permission with `permittedLocalities`, the same rules in one query, through `panelScope` (`src/core/review/scope.ts`), which says which permission each review screen needs. A screen with nothing the user may see answers `forbiddenResponse()` (`src/lib/access/admin-gate.ts`) before reading any card; a card or edit of a locality the user may not see answers the same 404 as one that does not exist. The local identity `admin@enmirumbo.test` is a panel user like any other: without a user and a role in the database it gets the 403 (README, Admin panel). A new permission goes in `PERMISSIONS` (`src/core/access/permissions.ts`) and in a migration, in the same pull request; `test/worker/access.test.ts` compares them. No email, phone number or other data of a real person goes in the repository.
- Panel rectification (`src/core/review/rectification.ts`) uses `RegistrationForm.astro` in `panel` mode and `validateBusinessFields`, never a fork: no public anti-bot fields or consent, direct saves in any status with `businesses.edit`, pending owner edits untouched, and contact changes audited atomically. Published cards require a catalogue zone of their locality, hidden zones marked "(oculta)" included; the shared form omits its free-text option there, and the save rechecks the invariant under the card lock. Cards in review or rejected keep the registration's zone behavior. The data-copy link (`src/core/review/data-copy.ts`) also needs `businesses.edit` in the card's locality and includes only the allowed captured fields, trades, notice acceptance and photo presence, never internal review data or the photo address.
- Admin pages live under `src/pages/admin/`, read through `HYPERDRIVE_FRESH`, and build their links with `src/core/review/paths.ts` (the zones screen, with `src/core/zones/paths.ts`). Admin actions live under the `admin` key of the actions object, and each handler starts with `const admin = await requireAdmin(context)` (`src/lib/access/require-admin.ts`): actions are reachable outside `/admin`, so the middleware alone does not protect them. Admin forms post to a page under `/admin`, because Access only adds its token to requests for `/admin` and below; a call to `/_actions/admin.*` carries no token and is refused. Like a public form's, an admin action decides only from its page (`context.routePattern`, as `reviewTarget` and `deletionTarget` in `src/lib/review.ts` do) and finds what it touches by the page's address, never a field; then it checks its own permission again in that card's locality (`cardToDecide`, `src/core/review/decision.ts`; for a pending edit, `editToResolve`, `src/core/review/edit-decision.ts`), whatever the page showed, and changes a status only with one conditional write on the status it expects, never a read and then a write. A transaction that writes a card and a pending edit of it locks the card first, as the owner's save does (`src/core/edit/save.ts`, `applyEdit` in `src/core/review/apply.ts`), so two of them wait for each other instead of deadlocking. A destructive action writes its entry of the audit log (`admin_audit_log`: the Access email, the locality, the card, the action and the previous status, never the card's data) in the same transaction, as `rejectRegistration` (`src/core/review/rejection.ts`), `unpublishCard` (`src/core/review/unpublish.ts`) and `deleteCard` (`src/core/review/deletion.ts`) do; the entry has no foreign key to the card and outlives its deletion. A permanent deletion deletes the photos first, then the rows in one transaction, and never says it deleted what it did not (deployment, "Permanent deletion refuses to claim it deleted what it did not delete"): a screen it lands on carries nothing of the deleted card, not even its identifier.
- The texts of the privacy notice and the terms are data in `src/core/legal/`, equal to the verbatim blocks of `docs/specs/legal-pages.md`: change both together (`test/scripts/legal-texts.test.ts` compares them). Any change to what the notice publishes, a placeholder filled in or the draft mark removed included, raises `NOTICE_VERSION` in `src/core/legal/version.ts`, the only place the version is written, and adds a row to `FINGERPRINTS` in `test/scripts/notice-version.test.ts` with the fingerprint its failure prints. Never edit the row of a published version.
- A page that belongs to no locality and reads no database may be prerendered (`export const prerender = true`), like the legal pages. Cloudflare serves it without the Worker, and the build of a deployed environment gives it `X-Robots-Tag: noindex` through `_headers`. A prerendered page never reads the database: the build of a deployed environment fails if it tries.
- Do not build anything that `docs/PRD.md` lists as out of scope.
- The repository is public. Never commit secrets, tokens, account ids, or real business names or phone numbers. Seeds and tests use fictional data.
- The repository holds only what the project runs (the application, its workflows, migrations, the seed and the development tooling) and the operating documentation a contributor needs. No one-off script or SQL statement goes in it, nor in a pull request description, which is public too.
- Cloud resources (buckets, hostnames, tokens, Hyperdrive configurations, Workers) are named in English. A hostname uses subdomains while it stays one level below its zone, because Cloudflare's free Universal SSL certificate covers only the zone and one level of subdomain ([Advanced Certificate Manager](https://developers.cloudflare.com/ssl/edge-certificates/advanced-certificate-manager/)); deeper levels are flattened with hyphens: the ideal `media.dev.enmirumbo.urekz.com` is `media-dev-enmirumbo.urekz.com` under `urekz.com`, and `media-dev.enmirumbo.com` under `enmirumbo.com`. Until `enmirumbo.com` is on Cloudflare, anything that needs a domain uses a hostname under `urekz.com`, set only through configuration.
- Secrets live only in the GitHub Environments `dev`, `stage`, `prod` and `backup` (ADR 0020). A workflow step gets only the secrets it needs, through its own `env:`, and never prints one. A Worker secret is declared in `secrets.required` at the top level and in each Wrangler environment, passed to the Deploy step of each workflow through its `env:`, and uploaded by `scripts/deploy/deploy-worker.sh` with `wrangler deploy --secrets-file`.
- Dependencies use exact versions. Only `esbuild` and `workerd` may run install scripts (`allowBuilds` in `pnpm-workspace.yaml`). `vite-plus`, Vite+ core and `vitest` are upgraded together through the catalog in `pnpm-workspace.yaml`.
- Oxfmt formats every file except `.astro`; Prettier formats only `.astro` files. Do not add a `.prettierignore`: Oxfmt reads it too.
- A change to behaviour updates `docs/specs/` in the same pull request. A behaviour change big enough to discuss lands first as a docs-only pull request.

## Branches and pull requests

- One trunk, `main`. One short branch per Plane work item, named `EMR-<n>-<description>`.
- Pull request titles start with the work item key, for example `EMR-13 Scaffold the repository`. Pull requests are squash merged after a review by someone other than the author.
- Commits are signed.
- Agents leave a receipt in the pull request: what they read, changed and verified, and what it cost.
