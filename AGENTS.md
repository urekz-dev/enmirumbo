# enmirumbo

Hyperlocal business directory: Astro in server mode on Cloudflare Workers, built with Vite+. [README.md](README.md) explains how to run it.

- Product intent: [docs/PRD.md](docs/PRD.md).
- Behaviour: [docs/specs/](docs/specs/). When the PRD and a specification disagree, the specification wins on behaviour.
- Decisions: [docs/adr/](docs/adr/).

## Commands (Vite+)

- `vp install`: install dependencies. Its `prepare` script runs `vp config`, which installs the pre-commit hook (`vp staged`).
- `vp check`: format (Oxfmt), lint (Oxlint) and type check.
- `vp run check:all`: `vp check`, Prettier on `.astro` files, `astro check`, and `wrangler types --check`. Run it before opening a pull request.
- `vp test`: tests inside workerd with `@cloudflare/vitest-plugin`.
- `vp run db:up`, `db:down`, `db:generate`, `db:migrate`, `db:seed`, `db:check`: the local PostgreSQL 18 (Docker), Drizzle migrations, the seed and the migration guard. `vp test` needs the database up.
- `vp run e2e`: build, then run Playwright against `astro preview`. Its global setup migrates and seeds `DATABASE_URL` (default: the development database), which turns Tizayuca on, and writes the seed's photos to the local media bucket. Run `vp exec playwright install chromium` once first.
- `vp run dev`, `vp run build`, `vp run preview`: Astro's dev server, build and preview. Never use `vp dev`, `vp build` or `vp preview`: they run plain Vite, which ignores Astro.
- `vp run fmt:astro`: format `.astro` files with Prettier.
- `vp run types`: regenerate `worker-configuration.d.ts` after a change to `wrangler.jsonc`, and commit it.

Vite+ documentation is in `node_modules/vite-plus/docs`.

When Astro detects a coding agent, `astro dev` and `astro preview` start in the background. Stop them with `vp exec astro dev stop` or `vp exec astro preview stop`.

## Layout

- `src/worker.ts`: the Worker entry. `fetch` goes to Astro (locally, `/_media/` first serves the local media bucket, `src/lib/media.ts`), adds the security headers (`src/lib/security-headers.ts`) and, outside local, `X-Robots-Tag: noindex` (`src/lib/robots.ts`); `scheduled` runs the hourly jobs in `src/scheduled.ts`: every task of `SCHEDULED_TASKS`, at the scheduled time, each deciding by the local day or hour of each locality, idempotent, and logging counts only. It also exports the `QuotaCounter` Durable Object of the per-IP quotas (`src/lib/quota/`), and so does `test/worker/entry.ts`. Static assets skip the Worker: the build gives them the same headers through `_headers` (`src/integrations/static-headers.ts`).
- `src/middleware.ts`: Astro middleware. It sends every request for `/admin` and below, and every admin action, through the Cloudflare Access check in `src/lib/access/`; then it resolves the active locality of every page under `/{estado}/{municipio}/` (`src/lib/locality.ts`), or answers 404.
- `src/actions/index.ts`: the Astro Actions, every mutation of the site. Astro runs an action before the page its form posts to, and the page reads its result.
- `src/pages/`: Astro routes. Every page renders inside `src/layouts/BaseLayout.astro`, which reads the locality from `Astro.locals`, writes the metadata (canonical, Open Graph, share image) and the Umami script where it applies, and adds the header and footer (`src/components/`). `/robots.txt` and `/sitemap.xml` (`src/core/seo/sitemap.ts`) are routes too.
- `src/styles/global.css`: the design tokens (Tailwind 4). Tailwind's default palette is off: use only the tokens; `test/scripts/design-tokens.test.ts` checks them and their contrast.
- `src/core/`: business rules and data access. It never imports `astro` or `astro:*` (an Oxlint rule enforces it). `src/core/db/` holds the Drizzle client (`withDb`), the schema and the seed; `src/core/legal/` the texts of the legal pages and the version of the privacy notice; `src/core/photos/` the photo key and the objects of a photo.
- `drizzle/`: generated migrations and Drizzle Kit's journal. `scripts/`: Node scripts for the database tasks.
- `.github/workflows/deploy-*.yml` and `scripts/deploy/`: the deploys to `dev`, `stage` and `prod` (README, Deployment). `monitor.yml`, `backup.yml`, `scripts/monitor/` and `scripts/backup/`: the availability check and the nightly backup of production (README, Operations). The shell scripts are tested in `test/scripts/deploy-scripts.test.ts` and `test/scripts/operations-scripts.test.ts` and pass ShellCheck.
- `test/worker/`: Vitest tests inside workerd. They load `test/worker/entry.ts` instead of `src/worker.ts`, because Astro's handler only resolves inside an Astro build.
- `test/astro/`: Vitest tests that render Astro components with the Container API, in Node.
- `test/e2e/`: Playwright tests. Those in `test/e2e/search-pages/` run alone after the rest, because they add published cards to Tizayuca that the sitemap would list; those in `test/e2e/two-localities/` run after them, with a second, fictitious active locality. `test/e2e/surfaces.spec.ts` crawls the site and checks every page it reaches against the layout rules.
- `worker-configuration.d.ts`: generated by `wrangler types`. Never edit it by hand.

## Rules

- Code, comments, documentation, commit messages, pull requests and Plane work items are in English. UI copy is in colloquial Mexican Spanish ("Registra tu negocio gratis", never "Crear listado").
- The brand is enmirumbo, one word, always lowercase. Never write "enmirumbo Tizayuca". Texts that name a locality read it from the locality record; never hard-code a locality name.
- The public site works without JavaScript. Only the registration and edit forms need it, and only while Turnstile's switch is on: then the form's submit button is `disabled` in the markup, a `<noscript>` above its fields says why, and the widget's script enables the button once it has a token; with the switch off they submit and validate on the server without it. Every check stays on the server either way. No React or other client framework; mutations use Astro Actions with `accept: 'form'`.
- Turnstile (ADR 0012): a form that needs it (the registration, and the edit form) renders `src/components/TurnstileWidget.astro` with `turnstileSiteKey(env)` and its own action from `TURNSTILE_ACTIONS` while the switch is on, and its core calls `checkTurnstile` (`src/core/turnstile/check.ts`) after the trap field and before anything else, with the connection of the action (`HYPERDRIVE_FRESH`) and `turnstileVerifier(env)` (`src/lib/turnstile.ts`). Never send the visitor's address to siteverify. The switch is `turnstile_enabled` in the one row of `site_settings`, read with `isTurnstileEnabled` (`src/core/settings/settings.ts`); a new switch is a new column there. Test keys count only with `ENVIRONMENT` `local`; never accept a dummy token anywhere else, and never commit a test key for a deployed environment. The report form and the search never include Turnstile. The end-to-end tests that open a page with the widget import `test` from `test/e2e/turnstile.ts`, which answers Cloudflare's origin with a local fake.
- A public form posts to its own page with its action (`method="post"`, `action={actions.<name>.queryString}`). The action checks that it was posted from its page (`context.routePattern`) and answers not found otherwise; what the page is about, such as a card, it reads from the page's address (`context.params`, as `reportTarget` in `src/lib/report.ts` does), never from a field. The page reads the result with `Astro.getActionResult`: a success answers a 303 to a page of its own (`seeOther`, `src/lib/locality.ts`), so a reload never sends the form again; an error renders the form again from the same submission. What a person wrote never goes in a cookie or an address: the privacy notice lists exactly two cookies. The trap field of a public form is `src/components/HoneypotField.astro`, checked with `isHoneypotFilled` (`src/core/forms/honeypot.ts`). No public form relies on the browser's validation: the server checks every field and shows each error next to it, in Spanish (a form with typed or required fields is `novalidate`, as the registration's is).
- Mobile first: design for a 390 px wide phone.
- Every public page of a locality lives under `src/pages/[state]/[municipality]/` and reads its locality with `requireLocality(Astro.locals)`; the middleware has already answered 404 for an unknown or inactive one (ADR 0007). Build internal links with `localityPath` (`src/core/locality/paths.ts`), and a card's with `cardPath` (`src/core/business/card-path.ts`), never as literal paths, and absolute URLs with `absoluteUrl` (`src/lib/site-url.ts`), which reads `SITE_URL`. A public page shows a catalogue zone by its display name, read with `localityZoneNames` and applied with `withZoneName` (`src/core/catalogue/zone-names.ts`), never by its stored name, which can repeat. Every list of businesses renders `src/components/ListingCard.astro` and shows `PAGE_SIZE` cards a page with `parsePage` and `pageSlice` (`src/core/pagination.ts`) and `src/components/MoreLink.astro`: `?pagina=n` from 2 on, and any other `pagina` or a page past the last answers 404.
- An indexable page passes its own path as `canonicalPath` to `BaseLayout`, which declares its absolute canonical URL and `og:url`; a 404 or the panel passes none, and a page that answers but must not be indexed passes `noindex`. An indexable page of a locality also adds its kind to `LOCALITY_PAGES` (`src/core/seo/sitemap.ts`), the only list the sitemap reads; `test/e2e/seo.spec.ts` fails when a URL of the sitemap does not answer 200. A page of a locality that crawlers do not need goes in `LOCALITY_DISALLOW` (`src/lib/robots.ts`); never list the edit mode there.
- The share image of a locality is one static 1200×630 PNG at `src/assets/share/{estado}/{municipio}.png`, made as the README says; no code names it, and no generator script is kept.
- The content security policy (`src/lib/security-headers.ts`, `docs/specs/deployment.md`) allows no inline script or style and no external origin but Turnstile's, Umami's (production with a Website ID) and the media hostname (`MEDIA_URL`): never add a `style` attribute, an `is:inline` script or a resource from another origin. The only `<script>` tags a page writes itself are the Schema.org data block of `src/components/JsonLd.astro`, which browsers never run, and the processed `<script>`s of `src/components/RegistrationForm.astro` and `src/components/TurnstileWidget.astro`, which Astro bundles as files under `/_astro/` (`assetsInlineLimit: 0` keeps them from being inlined); `test/e2e/surfaces.spec.ts` allows them on the registration page alone, with the request of the widget's script to Turnstile's `api.js`. A new origin changes the policy, its tests and the spec in the same pull request.
- Analytics (ADR 0014): only production with `UMAMI_WEBSITE_ID` loads Umami, never the panel or the edit mode (`isMeasured`, `src/lib/analytics.ts`). Events use only the names of `ANALYTICS_EVENTS`, declared with `eventAttributes`, whose only properties are the locality and the category slug; never put text a person typed in them. A page view may carry one of `ANALYTICS_TAGS`, passed to `BaseLayout` as `analyticsTag`. A page that must not be indexed passes `noindex` to `BaseLayout`, and a title with no text a person typed.
- Per-IP quotas (ADR 0012): a page or an action asks with `takeQuota(env, request.headers, "<purpose>")` (`src/lib/quota/quota.ts`), the purpose written as a literal, and gives up when it is not allowed; each purpose has its own limit and window in `QUOTAS` (`src/core/quota/quotas.ts`), at most an hour, and the purposes are that fixed list, never built from a request. The counters and the key of their codes live in the memory of one single `QuotaCounter` Durable Object for every purpose, named `QUOTA_COUNTER_NAME`; the purpose is part of each counter's code, so each purpose counts apart. Never write an address or its code to its storage, the database or a log, or the privacy notice stops being true. The address is `CF-Connecting-IP`; tests send one from the ranges reserved for documentation (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`), since a loopback address is not counted.
- The quota counter must never run up a bill (ADR 0012, amended on 2026-10-15): reach `QUOTA_COUNTER` only as `getByName(QUOTA_COUNTER_NAME)`, never a Durable Object per visitor, address, user or purpose; the counter never uses `ctx.storage` and sets no alarm (`setAlarm`, `alarm()`); its one timer exists only while at least one counter exists, each arming is at most `MAX_TIMER_MS` ahead (under the 15 minutes for which a pending timer keeps an object in memory), and it is never set again once no counter remains; and `preview_urls` stays `false` at the top level and in every environment of `wrangler.jsonc`. `test/scripts/quota-guardrails.test.ts` and `test/worker/quota.test.ts` check them.
- Photos (ADR 0011): a page renders a photo only with the address `src/lib/media.ts` builds from `MEDIA_URL` and the stored key of a published card, never from a stored value as it is, and never reads a key of an unpublished one. The listing card shows the `card` variant, the card the `full` one (`src/core/photos/photo.ts`). Whatever writes a photo writes both variants under `photos/<key>/`, with `PHOTO_CACHE_CONTROL`. The public media bucket holds only public content, by prefix; anything private gets a bucket of its own. No image file goes in the repository but the share images: the seed draws its photos when it runs.
- Public URLs always carry the state and the municipality: no route takes a single segment, so there is no short alias (`test/scripts/internal-links.test.ts` checks it). The visitor's approximate location (`Astro.request.cf`) is only a suggestion: never redirect by it, store it or log it. A redirect that depends on the visitor, such as the one the locality cookie makes, is a 302 with `Cache-Control: no-store`, never a 301.
- Business rules and data access live in `src/core/`, which never imports Astro. Pages and Actions validate input, authorize the request and call the core (ADR 0019).
- Read bindings with `import { env } from "cloudflare:workers"`. Astro sessions stay off.
- `wrangler.jsonc`: the top level is the local Worker; `dev`, `stage` and `prod` each declare their own bindings, vars and triggers, because Wrangler does not inherit bindings or vars. A new binding or variable goes in the top level and in the three environments (`test/scripts/wrangler-config.test.ts` checks it); then run `vp run types`. Build for an environment with `CLOUDFLARE_ENV=<env> vp run build`. Never run `wrangler deploy` by hand: the deploy workflows are the only way to deploy.
- The application runs natively; only supporting services, such as PostgreSQL, run in containers through Docker Compose (ADR 0019).
- Migrations are additive only: never edit an applied migration, and never drop, rename, retype, make `NOT NULL` or truncate in the same version that stops using a column or table. The destructive change comes one version later, in its own pull request, with `-- destructive-ok: <reason>` in the SQL file; `vp run db:check` fails without it.
- The database generates `name_normalized` and `what_you_offer_normalized` with the SQL function `search_normalize`; no code writes them. The search normalizes what a resident types with `normalizeText` (`src/core/search/normalize.ts`), which must give the same text as `search_normalize`; `test/worker/search.test.ts` compares them.
- Use `HYPERDRIVE` (cached, 60 seconds, not invalidated by writes) only for public reads; the specs allow a public page to show a change up to a minute late, and the panel says so. Use `HYPERDRIVE_FRESH` for writes, the admin panel, verification flows and any read that follows a write. Get a database through `withDb`; never create a `pg` client by hand.
- A `DATABASE_URL` that leaves the machine must use `sslmode=verify-full`. Seeds hold fictional data, use `.onConflictDoNothing()` and never run against `prod`. Phone numbers in seeds, tests and examples follow `771999xxxx`.
- A schema change in `src/core/db/schema/` comes with its migration (`vp run db:generate`); `test/scripts/schema-drift.test.ts` fails otherwise. Every foreign key to `businesses` is `ON DELETE CASCADE`, so a permanent deletion (ARCO) leaves nothing behind; `test/worker/data-model.test.ts` checks it. A new business gets its identifier from `newBusinessId()` (`src/core/business/id.ts`).
- Reference data (categories, trades, and the state, municipality, locality and zones of each city the directory serves, today only Tizayuca) ships in data migrations; `vp run db:seed` only adds fictitious businesses. A new city ships its reference data in its own data migration. Tests create any other state or municipality they need, fictitious and with a state code above 32 (`test/worker/fixtures.ts`), and remove it. A new page of a locality adds its first path segment to `RESERVED_SEGMENTS` (`src/core/catalogue/root-urls.ts`); `test/worker/root-urls.test.ts` fails when a slug of the catalogues takes a reserved segment or makes a URL of a locality read in two ways.
- Admin authorization (ADR 0021): Access proves the email, the database decides what it may do. Check a permission with `can()` (`src/core/access/queries.ts`) in the locality of what the action touches; never check a role by name. A new permission goes in `PERMISSIONS` (`src/core/access/permissions.ts`) and in a migration, in the same pull request; `test/worker/access.test.ts` compares them. No email, phone number or other data of a real person goes in the repository.
- Admin pages live under `src/pages/admin/`. Admin actions live under the `admin` key of the actions object, and each handler starts with `const admin = await requireAdmin(context)` (`src/lib/access/require-admin.ts`): actions are reachable outside `/admin`, so the middleware alone does not protect them. Admin forms post to a page under `/admin`, because Access only adds its token to requests for `/admin` and below; a call to `/_actions/admin.*` carries no token and is refused.
- The texts of the privacy notice and the terms are data in `src/core/legal/`, equal to the verbatim blocks of `docs/specs/legal-pages.md`: change both together (`test/scripts/legal-texts.test.ts` compares them). Any change to what the notice publishes, a placeholder filled in or the draft mark removed included, raises `NOTICE_VERSION` in `src/core/legal/version.ts`, the only place the version is written, and adds a row to `FINGERPRINTS` in `test/scripts/notice-version.test.ts` with the fingerprint its failure prints. Never edit the row of a published version.
- A page that belongs to no locality and reads no database may be prerendered (`export const prerender = true`), like the legal pages. Cloudflare serves it without the Worker, and the build of a deployed environment gives it `X-Robots-Tag: noindex` through `_headers`. A prerendered page never reads the database: the build of a deployed environment fails if it tries.
- Do not build anything that `docs/PRD.md` lists as out of scope.
- The repository is public. Never commit secrets, tokens, account ids, or real business names or phone numbers. Seeds and tests use fictional data.
- Cloud resources (buckets, hostnames, tokens, Hyperdrive configurations, Workers) are named in English. A hostname uses subdomains while it stays one level below its zone, because Cloudflare's free Universal SSL certificate covers only the zone and one level of subdomain ([Advanced Certificate Manager](https://developers.cloudflare.com/ssl/edge-certificates/advanced-certificate-manager/)); deeper levels are flattened with hyphens: the ideal `media.dev.enmirumbo.urekz.com` is `media-dev-enmirumbo.urekz.com` under `urekz.com`, and `media-dev.enmirumbo.com` under `enmirumbo.com`. Until `enmirumbo.com` is on Cloudflare, anything that needs a domain uses a hostname under `urekz.com`, set only through configuration.
- Secrets live only in the GitHub Environments `dev`, `stage`, `prod` and `backup` (ADR 0020). A workflow step gets only the secrets it needs, through its own `env:`, and never prints one. A Worker secret is declared in `secrets.required` at the top level and in each Wrangler environment, passed to the Deploy step of each workflow through its `env:`, and uploaded by `scripts/deploy/deploy-worker.sh` with `wrangler deploy --secrets-file`.
- Dependencies use exact versions. Only `esbuild` and `workerd` may run install scripts (`allowBuilds` in `pnpm-workspace.yaml`). `vite-plus`, Vite+ core and `vitest` are upgraded together through the catalog in `pnpm-workspace.yaml`.
- Oxfmt formats every file except `.astro`; Prettier formats only `.astro` files. Do not add a `.prettierignore`: Oxfmt reads it too.
- A change to behaviour updates `docs/specs/` in the same pull request. A behaviour change big enough to discuss lands first as a docs-only pull request.

## Branches and pull requests

- One trunk, `main`. One short branch per Plane work item, named `EMR-<n>-<description>`.
- Pull request titles start with the work item key, for example `EMR-13 Scaffold the repository`. Pull requests are squash merged after a review by someone other than the author.
- Commits are signed.
- Agents leave a receipt in the pull request: what they read, changed and verified, and what it cost.
